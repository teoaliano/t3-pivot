# What a position is

Type: grilling
Status: resolved
Blocked-by:

## Question

Which fields make up a position, how is each validated, and what does a teammate keep of it?

Starting set: name, when to use (read by the Pivot when choosing), instructions (go into
the brief), model, outcome (reports back / delivers a change), skills, tools. Decide the
identity (stable id vs name, renames), required vs optional fields, limits on length, and
the exact snapshot a teammate stores at dispatch so a later edit or delete never changes a
running teammate. Check each field against the day-one positions in the map's Notes.

Code today: `TeammateKind` in `packages/contracts/src/pivot.ts`, `TeammateModelEntry` and
`TeammateKindModelSelections` in `packages/contracts/src/settings.ts`, the teammate record
in `apps/server/src/pivot/PivotStore.ts`.

## Resolution

**Decided 2026-11-02.**

### Fields

| Field        | Rule                                                                        |
| ------------ | --------------------------------------------------------------------------- |
| id           | Generated by the server at creation. Stable across renames. What the Pivot passes to `dispatch_teammate` and what a snapshot records. |
| name         | Required, at most 40 characters, unique across positions ignoring case.     |
| when to use  | Required, at most 500 characters. The Pivot reads it to choose.             |
| instructions | Optional, at most 20,000 characters. Goes into the brief.                   |
| outcome      | Required: reports back, or delivers a change.                               |
| model        | Optional `ModelSelection` (effort included). Empty runs on the Pivot's own model. |
| skills       | A list. What an empty list means is decided in Skill choices.               |
| tools        | On/off choices. What the default is is decided in Tool choices.             |

At most 30 positions. Their order in Settings is the order the Pivot reads them in. There's no
priority field.

**Model order at dispatch:** the Pivot's override (the user named a model), then the
position's model, then the Pivot's own model. If the chosen model's provider is unavailable,
the Pivot's own model is used, so dispatch never fails.

### Not on a position

No icon or colour, no enabled switch, no access-mode field, and no per-position concurrency
limit. Delete and restore covers parking a position. Access mode follows from the outcome and
the tools (Tool choices). Cards and concurrency stay in the map's fog.

### Environment only

Positions live only in environment settings, with no project override. This differs from
today: `teammateModels` and `teammateKindModelSelections` are in
`PROJECT_SCOPED_SERVER_SETTING_KEYS`. Migration must decide what happens to project overrides
that already exist. The project override for `pivotModelSelection` stays.

### The snapshot

At dispatch the teammate stores the whole resolved position: id, name, outcome,
instructions, the model it actually got, skills and tools. It never changes afterwards.

- A relaunch or a server restart reapplies the snapshot's skills and tools. This matters
  because tool limits are set when the provider session starts, and a relaunch today
  re-sends only a short message.
- Cards show the snapshot's name.
- Editing, renaming or deleting the position doesn't touch running or finished teammates.

### Module

One `TeammatePositions` service with two operations:

- `list()`: the positions in settings order, read by the Pivot and Settings.
- `resolve({ positionId, modelOverride, pivotModel })`: returns a `PositionSnapshot`.

`resolve` owns the lookup, the fallback for a missing or deleted id (target decided in How
the Pivot picks a position and Default positions), the model order and the
unavailable-provider fallback. Writes go through the existing settings update, and the schema
enforces the rules above. The teammate row replaces `kind` and `model_entry` with one
`position` snapshot column. Callers never read the settings array, so `PivotService`,
`LocalTeammateHost` and the brief stop branching on kind. Tests exercise `resolve` alone.

## Amendment from What stays fixed in the brief (2026-11-03)

- Instructions are **required** (at most 20,000 characters).
- A position that reports back has a **workspace** field: own worktree (the default) or project
  checkout, read-only. It's in the snapshot. This is an exception to "Not on a position".
